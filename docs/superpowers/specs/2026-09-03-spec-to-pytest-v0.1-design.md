# spec-to-pytest v0.1 — 开源首版设计规格

日期：2026-09-03  
状态：2026-09-03用户已确认书面规格；进入分阶段实现与验收。
用途：约束首版实现与验收。本文描述目标设计，不宣称这些能力已经实现。

## 1. 定位、用户与成功标准

**spec-to-pytest 是一个本地优先的 AI 辅助测试工作台：将业务场景转化为可审阅的
Python Playwright 测试，并核对从计划、探索、生成到执行的证据。**

主要服务于希望将 AI 接入现有自动化框架的 QA/SDET 和学习者。项目同时是一个可供
招聘方技术验证的个人作品，不包装成生产落地经验、通用自主测试平台或覆盖率提升承诺。

首版须让使用者回答四个问题：测什么、生成了什么、实际执行了什么、结果如何证明。
没有 TRAE 或模型账号的使用者，也必须能运行本地应用、人工基线和已审阅的生成样例。

### 路线选择

- 采用：轻量工作台，复用已有框架，增加可复现环境、机器结果核对和协作资料。
- 不采用：仅整理 README；不能解决已有安装、测试隔离和结果可信问题。
- 不采用：多租户 SaaS、Agent 调度服务或通用测试平台；超出个人首版维护范围。

首版不新增模型 API SDK、注册/付费系统、向量数据库、任务队列、推荐算法或外部站点
测试。交易扩展、WireMock、Jenkins 和 Docker 留在原参考工程，暂不进入新发布目录。
不提供 PyPI 安装承诺，首版按源码仓库工作台交付。

## 2. 迁移与保护边界

新目录名和拟用 GitHub 仓库名均为 `spec-to-pytest`。保留原演示工程及原参考工程，
新工程不通过软链接、共享可写数据或父目录导入依赖它们。

本规格先在新本地仓库中独立提交。规格通过后按白名单复制应用、框架、核心测试和必要
资产；不复制 `.git/`、虚拟环境、缓存、本地 MCP 配置、环境文件、数据库或原始报告。
原有 13 条生成测试和相应计划/CSV只作为候选迁移资产，必须审阅、迁移契约并重新运行，
不能直接当作首版已通过的证据。

新提交使用不暴露私人邮箱的提交身份，只配置新仓库，不更改用户全局 Git 配置。
原代码来源、保留内容、重写内容和已知设计差异写入来源说明；干净 Git 历史不代表
抹除作者归属。遇到无法确认分发权限的第三方代码或素材，排除该资产，不能擅自加许可证。

## 4. 两个运行入口与 Agent 调用关系

### 4.1 不需要 AI 的入口

锁文件安装依赖后，一条运行命令启动自有本地服务并运行基线或已审阅样例，生成
JUnit、Allure原始结果和汇总。此入口不要求 Node、TRAE、模型账号或 API Key；不能
将这种重跑标成一次新的 AI 生成。重跑器将已审阅样例复制到本次生成目录，保持测试
内容与来源Hash不变；本次run_id作为执行元数据传入，不伪造新的模型生成记录。
生成目录明确加载与人工测试相同的受维护Fixture，不能依赖调用者碰巧从某目录启动。
静态 HTML Allure报告是显式可选步骤，不阻断原始
结果生成，安装要求另列。

### 4.2 TRAE 辅助生成入口

标准入口由 TRAE 内置 Agent 协调两个自定义角色。协调器按明确阶段分派，而不是假定
自定义Agent之间可以直接互调。执行顺序如下：

1. 协调器创建 `run_id`，调用测试生成器形成候选计划并返回计划路径。
2. 协调器调用数据增强器；增强器读取数据增强Skill、业务规则和计划，返回CSV及校验结果。
3. 协调器把计划和数据交回测试生成器，完成预检、MCP探索和Python生成。
4. 测试生成器调用确定性执行入口、在允许范围内修复；协调器取得执行器汇总。

| 角色或工具 | 做什么 | 不做什么 |
|---|---|---|
| TRAE内置Agent | 分派两个角色、传递已落盘文件、控制阶段 | 不凭自然语言宣布通过 |
| Playwright AI测试生成器 | 设计候选用例、探索、生成代码、提出有限修复 | 不修改被测系统、规则或已冻结预期 |
| AI测试数据增强器 | 等价类、边界、异常和必要组合数据 | 不操作浏览器、不执行测试、不决定通过 |
| 数据增强Skill | 提供可复用操作步骤和输出契约 | 不主动发起调用、不自动创建独立上下文 |
| Playwright MCP | 读取页面结构并实际操作浏览器，提供探索上下文 | 不提供最终测试结果或完整安全隔离 |
| Pytest与汇总器 | 执行断言、采集阶段结果、核对计划和证据 | 不调用模型、不把解释当事实 |

兼容入口允许使用者直接调用测试生成器，由它读取同一Skill完成数据增强。运行元数据
分别记为 `trae_orchestrated` 或 `trae_single_agent_skill`。未发生子Agent调用时不可
记录为“双Agent执行”。标准入口和兼容入口的支持状态分开记录，未实测的入口不标为
可用；首版完整AI演示至少要验证标准入口。

正常场景一次输入后自动处理整批；宿主的权限、登录和额度限制仍可能要求人工操作，
不能承诺绕过这些检查。规格冲突或超出本地靶场范围时保留未执行原因，不擅自扩大目标。

### 4.3 MCP兼容性

锁定并实测具体MCP发行版本；在启动检查中核验版本、参数解析、工具列表及本地导航。
当前官方README列有 `--codegen python`；旧检索摘要出现过不同列表，不能据此推断
用户已安装版本。支持时保留Python代码提示，但最终仍由生成器整合成符合框架的测试。
教程不得以 `@latest` 代替已经验证的版本。

使用独立浏览器状态，不连接个人Chrome登录会话。默认目标为精确的loopback地址和
配置端口；不允许任意外站、file URL、共享浏览器或无限制文件访问。
`--allowed-origins`只是辅助限制，不是对重定向、恶意代码或提示注入的完整防护。

## 5. 输入、计划、数据与知识

### 5.1 场景和用例计划

场景提供目标、前置条件、业务范围和禁止事项。每条业务规则有稳定 `rule_id`，计划中的
每条用例必须引用规则或说明其探索性目的。默认每个场景8～15条候选用例；范围确实较小时
允许少于8条，但需在计划中写明原因。用例数量不能替代测试设计质量。

TestPlan采用 `schema_version=2.0`，至少包含 `run_id`、`scenario_id`、生成来源、
`cases`；每条case包含唯一 `case_id`、标题、优先级、规则引用、前置、步骤、预期、
数据引用及能否自动化。拒绝空计划、重复ID、混用scenario和无原因的不可执行项。

测试收集前冻结计划、规则、CSV和支持代码的内容Hash。修复不能偷偷删用例、改预期或
更换边界数据。若需求确实改变，创建新的run并关联旧run，而不是改写原计划。

### 5.2 数据增强

使用有效/无效等价类、上下边界、刚好越界、空白、Unicode、状态及高风险组合。
保留基准数据，去重后写新文件。明确区分计划的 `case_id` 和数据行的 `data_id`，
一个用例可引用多行数据，不把CSV行数当作测试数。新CSV统一使用 `data_id`，旧CSV
在迁移时显式转换，不静默混用契约。

数据校验覆盖字段、类型、ID唯一性、业务规则一致性与引用完整性；失败时修复候选
数据，不修改基准规则。`expected_valid`仅表示输入是否合法，不等同于整个场景通过。

### 5.3 MCP探索和步骤知识

探索是操作真实本地页面的预演，不是只在模型里模拟；目的是确定页面入口、定位器、
交互步骤和可观察结果，为代码生成提供证据。它可能改变测试数据，因此使用独立探索
实例或数据库，正式Pytest不得继承探索的登录态和业务状态。

先读取步骤知识，再读取当前页面快照验证定位器仍适用。缓存中的临时元素引用不可
直接跨会话使用；保存的是可重新解析的语义定位方式。已有知识过期时重新探索。

探索成功的步骤先写 `candidate_steps.json`。只有关联的正式用例验证通过，且步骤
验证记录完整时，才合并到本地可复用知识；包含去重键、应用版本、来源run/case、
验证时间和证据引用。失败尝试保留在本run，不推广为成功经验。

仓库中的知识样例只读；新的知识写入忽略的 `.local/knowledge/`。单元测试使用临时
知识库，不能假定使用者真实知识库永远为空。

## 6. 正式执行、状态和证据核对

### 6.1 运行目录

每次运行用新的不可复用 `run_id`；同一run中每次执行使用新的 `attempt_id`。

```text
reports/runs/<run_id>/
├── run.json                 # 执行环境与输入Hash，不含秘密值
├── plan.json / data.csv     # 冻结的输入快照
├── exploration/             # 探索日志与候选步骤
├── attempts/<attempt_id>/
│   ├── source/              # 本轮生成代码快照
│   ├── collection.json      # case_id与Pytest nodeid映射
│   ├── events.jsonl         # setup/call/teardown机器结果
│   ├── process.json         # 命令、退出码、超时与结束状态
│   ├── junit.xml
│   ├── allure-results/
│   └── artifacts/
├── repairs/                 # 补丁、分类、前后Hash、对应轮次
├── manifest.json            # 汇总器根据机器结果生成
└── summary.md               # 人可读摘要及限制
```

新轮次不得清空旧Allure目录；不使用“取最后一个junit.xml”猜测哪一轮生效。
所有被引用的路径必须是run内相对路径，拒绝绝对路径、目录穿越和越界软链接。
文件Hash用于核对意外不一致，不提供对本机高权限恶意修改者的防篡改保证。

### 6.2 计划与执行对应

使用明确的Pytest标记和结构化属性关联 `case_id`，不能靠文件名字符串猜测。
首版每个计划用例对应一个测试nodeid；参数化多个nodeid时必须拆分为独立case_id，
否则收集校验失败。纯数据循环仍属于一个case，其统计含义在文档中说明。

汇总器同时核对冻结计划、收集清单、Pytest事件、JUnit和进程退出信息：

- 计划内可执行case必须恰好映射一个nodeid；计划外、重复、遗漏均不能生成绿色汇总。
- 每个已收集nodeid的各阶段状态必须可解释；不能只看call阶段而忽略teardown失败。
- JUnit与事件数量、nodeid映射、状态冲突，或者进程非正常结束时，写完整性错误。
- 缺少JUnit、解析失败、零收集、执行被中断和被截断日志不能被解释为“全部通过”。
- 环境未能启动时生成明确的阻塞结果，不伪造一份表示通过的JUnit。

### 6.3 最终状态与退出规则

| 状态 | 由何种证据决定 |
|---|---|
| passed | 最终验收轮setup/call/teardown成功，映射与证据检查均通过 |
| failed | 执行器报告断言/测试失败；teardown错误也阻止该用例通过 |
| skipped | 冻结计划事先声明不可执行且有原因，或非核心用例有事先批准的跳过策略 |
| blocked | 环境/浏览器不可用、启动失败、中断、收集/映射错误导致无法可信判断 |

用例内部新增skip/xfail、断言失败后改为skip，以及缺少任何最终结果，都不能算正常
skipped；记录完整性错误并阻断汇总。至少区分环境阻塞、执行错误与应用缺陷候选，
不能把每个浏览器超时直接称为产品缺陷。

`manifest`统计的是唯一计划case，而不是重试次数。每条case保留尝试引用、最终轮次、
最终状态、分类、原因与证据可用性；所有计划case必须出现且只能出现一次。
`completed`仅表示汇总已结束，另设 `quality_gate=passed|failed|blocked`。

门禁通过必须满足：完整性通过、无failed/blocked、必测用例无skip、至少执行一条用例。
核心首版案例不允许skip。普通运行成功返回0，测试/门禁失败返回1，环境或完整性阻塞
返回2；如单个run兼有测试失败与阻塞，阻塞优先。原始Pytest退出码独立保留。

### 6.4 修复与最终验收轮

最多3轮自动修复，不含初次执行；每轮保存错误证据、允许的分类、diff与前后代码Hash。
定位器、等待、导入和语法可以调整；唯一测试数据的构造可调整，但不能改变冻结的
边界输入或业务预期。无法明确归类为基础设施问题时停止自动修复并保留失败。

规则、被测系统、人工基线、Schema、共享Page Object/Workflow均不允许在生成运行中
修改。它们可以在独立的人工维护任务中正常更新，不能与本次“修复至通过”混在一起。
对可解析代码，保护断言AST和调用到的业务校验块；检测到skip、xfail、断言删除或
受保护文件Hash改变时停止。初始代码无法解析时可先修语法，解析后立即建立断言基线。

静态检查不能证明语义不变；生成器仍可能一开始就写错断言，因此样例入库需要人工
审阅和已知缺陷验证。项目不会将这些检查宣传为抵御任意Python代码的安全沙箱。

修复过程中可针对失败case进行诊断重跑，但最终通过必须来自修复完成后的整批验收轮，
不能拼接不同版本的单条通过结果。`passed_after_repair`作为附加信息保留，不隐藏失败史。

### 6.5 采集失败

失败用例优先保留截图、Trace、视频和脱敏网络摘要。浏览器创建失败时可能没有媒体，
必须写明 `artifact_unavailable_reason` 并保留进程/Fixture错误。证据采集异常不能
覆盖原始测试异常。setup和teardown错误也必须出现在摘要中。

## 7. 本地被测系统与运行隔离

保留内容发布、搜索、点赞、评论和登录；原dashboard仅作为回归兼容页面，不增加功能。
业务规则保留现有长度与标签约定，并给出一致的API错误结构和页面反馈。

### 7.1 图片与内容持久化

正文数据使用SQLite；媒体放在同一应用数据根目录下的独立子目录。默认手动探索使用
`.local/app/`，正式测试使用run专属目录。复位仅作用于已验证的该实例数据根目录，
不接受任意外部删除路径。

PNG/JPEG先按2 MiB上限流式读取，再验证实际图片内容与类型，不只相信扩展名或MIME。
使用服务端生成的文件名，拒绝损坏图片和超出像素预算的解码；像素上限固定为20MP。
重新编码已接受图片，移除EXIF等元数据。信息流展示真正的图片资源；测试验证解码、
显示尺寸、资源归属和发布后可见，不能只断言文件名。

成功发布的内容和图片在同一数据目录重启后保留；失败发布不留下可访问孤儿媒体。
登录会话不承诺跨重启保留，重启持久化测试重新登录。数据清理使用专用实例接口或
仓储Fixture，不能清空其他run。

### 7.2 会话和测试控制

使用不可预测的服务端会话标识，不直接把用户名cookie当作登录身份；退出后旧标识
失效，cookie使用HttpOnly和SameSite策略。权限测试覆盖匿名与已登录状态；不新增
复杂RBAC。保留原角色字段及已有dashboard行为，不擅自把viewer定义成社区只读角色。

应用仅绑定loopback，不开放公网部署入口。浏览器写请求校验来源；测试客户端按照
同一约定构造请求。测试复位接口仅在显式测试模式启用，并要求实例控制凭证；该凭证
只在本机进程间传递，不进入公开配置、结果摘要或屏幕演示。

### 7.3 服务生命周期

运行器启动并拥有本次应用进程，核验application_id、版本、数据实例与bug_mode。
端口可配置且必须与BASE_URL一致；端口被占用时明确失败，不自动复用任何返回200的
现有服务，也不终止不属于本次run的进程。退出时只停止自有子进程并等待退出。

首版正式套件串行运行，显式拒绝多worker选项。每条用例独立清理本run的业务数据并
使用独立浏览器上下文；验证正常、反序和单条执行。共享生成工作目录加互斥运行锁，
发生冲突时提示使用独立副本，不以覆写文件解决。并发worker支持属于后续版本。

## 8. 首版样例与量化边界

提供三个案例，全部从同一套明确业务规则派生：

1. 健康主链路：登录、真实图片发布、搜索、点赞切换、评论及数据持久化。
2. 边界与匿名权限：标题/正文/评论边界、空白、标签去重、非法图片与未登录访问。
3. 已知缺陷：开启 `comment_counter`，评论已保存但计数未更新；原断言应失败且不能自动改为通过。

缺陷演示用外层回归测试验证“子进程非零＋指定case的评论计数断言失败＋证据存在”，
外层测试通过只证明缺陷演示有效，不能把内层失败报告改绿。正常模式和缺陷模式使用
独立进程、数据目录和run_id。

至少保留一次真实TRAE生成的、经过审阅的批次；记录操作日期、可见的TRAE/模型版本、
MCP与Python依赖版本、场景、提示词版本及人工介入。宿主不暴露模型精确版本时写
`not_exposed_by_host`，不猜测。未拿到实际TRAE执行记录前，不能声称完成AI端到端验收。

健康样例在锁定环境中连续运行3次，报告实际次数、case数与结果；这只是小样例重复性
证据，不是无flaky保证。首版不宣称节省百分之多少时间、达到多少覆盖率或适用生产。

## 9. 安装、CI与开发者体验

Python支持范围目标为3.12～3.14，使用 `pyproject.toml` 与 `uv.lock`作为唯一依赖
事实来源。首版至少在Linux/Python3.12与本机Python3.14验证；CI增加3.14的单元验证。
锁文件严格安装失败必须失败，不静默升级。废弃不可解析的旧requirements.lock，不维护
两个独立手工锁文件。第三方弃用警告要使用经验证的兼容组合或精确豁免，不全局吞警告。

拟交付命令包括 `make setup`、`make check`、`make baseline`、`make replay`、
`make bug-demo`和 `make report`。这些是后续实现的接口约定，不是当前可运行命令。
每个命令在帮助中写清依赖、输入、输出、清理范围和退出码；setup明确提示浏览器下载。

CI分三类：代码质量与unit/contracts；API/Chromium核心回归；秘密扫描与文档链接检查。
CI只跑确定性基线和已审阅生成样例，不登录TRAE、不访问外部业务系统、不需要模型密钥。
工作流令牌默认只读，不使用带写权限执行不可信PR代码的触发方式；固定Action版本。

失败产物按工作流run隔离，保留7天。公开CI只使用合成测试数据，并提供已脱敏的发布
摘要；原始Trace/录像不默认上传到公共仓库或Pages。CI真正跑通后才增加状态徽章，
本地通过不能冒充GitHub Actions已通过。

## 10. 文档、来源、隐私与发布

### 10.1 文档层次

英文README首屏说明解决的问题、适合谁、运行入口、真实效果和限制；提供中文入口。
文档分为Quickstart、Concepts（含各目录及角色关系）、How-to（TRAE、定位失败、
增加业务场景、审阅生成代码）、Reference（契约/命令/配置/支持矩阵）。

保留3个案例的可审阅测试与数据，展示真实本地页面和报告，不用概念图冒充运行截图。
新增贡献指南、行为准则、问题与PR模板、变更日志、路线图和安全报告说明。
`SECURITY.md`区分本地靶场、生成代码执行、MCP宿主权限和发布制品隐私；不承诺安全认证。

来源说明引用罗梓钰的TRAE实践文章，解释独立实现和工程增强点。保留MCP探索、步骤知识、
Pytest/Allure及数据增强的核心方法；明确本工程为兼容预先冻结计划，将数据增强前移，
与文章中先生成初始用例再扩写数据的顺序不同，不宣传为作者官方仓库或逐字复刻。
不直接复制长篇提示词、文章截图或没有明确分发许可的素材。

### 10.2 敏感信息门禁

忽略 `.env`及本地变体、个人MCP配置、认证状态、运行数据库、原始报告、浏览器数据和
缓存；只提交无凭证模板。公开配置使用合成演示身份，不需要使用者提供个人API Key。

发布检查覆盖暂存区、全部拟公开历史、打包文件，以及图片/截图/Trace/视频。检查
密钥、私钥、Cookie、请求头、个人路径、主机名、邮箱和外部账号信息；输出脱敏类别与
位置，不打印秘密值。精确允许已说明的演示账号，不宽泛忽略所有password/token字段。

先使用成熟秘密扫描器，再人工检查命中及媒体；扫描无命中不等于不存在秘密。若发现
真实凭据，停止发布并让所有者吊销/轮换，清理文件不能替代轮换。原始报告保留在本地，
仅通过显式白名单导出经过审阅的公共摘要和媒体。

软件漏洞审计与秘密扫描分开记录：若专用审计工具不可用，必须公开说明未完成项；
不能把工具启动检查通过或启发式无命中写成“安全审计通过”。

### 10.3 发布与社区

许可证候选为MIT，但最终选用必须在代码/素材来源核验和用户确认后进行；在此之前不
把无明确许可的仓库描述为已完成开源发布。仓库描述和topics围绕Python、Playwright、
Pytest、AI-assisted testing与TRAE，不堆无关标签。

准备3～5个真实小任务，每项说明复现、期望变化和验收；例如新增一条可验证业务规则的
样例、完善一条排错文档或补充特定平台验证。不能刻意留下已知缺陷制造贡献机会。
准备LinkedIn技术复盘草稿及社区分享材料，不自动发帖、买星、互星或批量提交推广PR。
